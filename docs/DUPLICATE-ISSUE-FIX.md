# Исправление повторной выдачи сканера

## Первопричина

В `app.js`, `submitIssue()`, действие «Переоформить» вызывало `performIssue()` напрямую. Проверка `existingWorkerDev` выполнялась только в обычной ветке выдачи, а само сохранение не проверяло другие устройства получателя. Поэтому переоформление TEST-A с сотрудника A на сотрудника B, у которого уже был TEST-B, записывало вторую активную выдачу в IndexedDB и очередь, после чего показывало «ВЫДАНО В СМЕНУ».

В `data.js`, `saveDeviceChanges()`, проверялись версии изменяемых сканеров, но не уникальность выдачи получателю. Этого недостаточно и для двух вкладок: у них могут быть актуальные версии разных сканеров, выдаваемых одному сотруднику.

Серверная `scanner_private.apply_operation()` уже запрещает несколько активных сканеров у одного получателя, проверяет версии, сериализует операции и применяет замену атомарно. Клиентская операция отклонялась как конфликт. `syncNow()` сохранял её в очереди и останавливал зависимые отправки. Серверное ограничение корректно; изменение RPC, RLS или миграций для этого исправления не требуется.

## Воспроизведение до исправления

На исходном коммите `afc50adc3523fa20fdd9a77597025ec931e36b18` добавлен и запущен тест:

```sh
PLAYWRIGHT_CHROMIUM_EXECUTABLE=/usr/bin/chromium npm run test:browser -- --grep 'reassignment cannot'
```

До изменения клиентского кода тест упал: ожидалось `ОПЕРАЦИЯ ОСТАНОВЛЕНА`, фактически интерфейс показывал `ВЫДАНО В СМЕНУ`. Тот же регрессионный тест после исправления проходит и проверяет отсутствие второй выдачи, новой записи истории и пакета в очереди.

## Изменения

- `core.js`: общая проверка итогового набора выдач `assertSingleActiveIssue()`. ID получателей сравниваются без учёта регистра и крайних пробелов. Списанные устройства не считаются активными. Проверяется весь итог операции, поэтому возврат старого и выдача нового сканера в одном пакете разрешены.
- `app.js`, `performIssue()`: проверка выполняется и при переоформлении. Отображение новой выдачи происходит после успешной транзакции IndexedDB, а не до неё.
- `data.js`, `saveDeviceChanges()`: проверка версий и уникальности получателя выполняется внутри одной пишущей транзакции `devices + queue + moves`. Ошибка отменяет всю транзакцию. Проверка защищает и от конкурентных выдач разных сканеров в двух вкладках.
- `app.js`, `submitIssue()` / `confirmSwap()`: сохраняются версии двух сканеров, показанных при выборе замены; изменение версии требует повторного выбора. На время сохранения замены действует блокировка операции. Закрытие диалога очищает ожидающую замену.
- Выдача, замена и их отмена явно обозначают локальное сохранение. Индикатор показывает «Сохранено локально · ожидает синхронизации», а «Подтверждено сервером» — только после отправки очереди и успешного получения состояния облака. Ошибка показывает причину, конфликт — уведомление и постоянный статус. Локальное сохранение не выдаётся за серверное подтверждение.
- `sw.js`: повышена версия кэша статических файлов. Публикация не выполнялась.
- Браузерная имитация Supabase дополнена проверкой уникальности получателя, атомарным применением пакета, идемпотентностью по ID и имитацией потери ответа после успешного применения. Клиентская проверка из `core.js` в имитации сервера не используется.

История и существующие пакеты не переписываются. Новая очередь использует прежний формат, подпись и идентификатор операции. При повторе отправляется тот же пакет. Сохранена ранее доступная настройка автоматической замены: если она явно включена, замена также проходит все проверки и сохраняется одним пакетом.

## Выполненные проверки

| Сценарий | Результат и доказательство |
| --- | --- |
| Первая выдача | Одна локальная выдача и один пакет; серверное подтверждение появляется только после синхронизации. |
| Повторная выдача | Повторный скан не добавляет пакет. Переоформление на уже оснащённого получателя блокируется без изменения истории и очереди. |
| Подтверждённая замена | Старый сканер освобождается и новый выдаётся одним пакетом с двумя изменениями. Существующий тест также проверяет отправку двух изменений одним RPC. |
| Отмена замены | Закрытие диалога ничего не записывает и очищает ожидающую замену. Ctrl+Z после локального сохранения добавляет отдельную атомарную обратную операцию; история сохраняется. |
| Устаревшая версия при подтверждении | Замена отклоняется до сохранения; оба устройства сохраняют актуальное состояние. |
| Отказ IndexedDB при записи очереди | Принудительная ошибка `queue.add()` откатывает оба устройства и обе записи локального журнала. Частичного применения нет. |
| Выдача без интернета | Сохраняется локально; существующие тесты проверяют сохранение после перезагрузки, восстановление офлайн-сеанса и последующую синхронизацию. |
| Отказ сервера | Имитация ошибки RPC показывает причину и сохраняет исходный подписанный пакет и локальную историю; последующий успешный повтор отправляет этот пакет. |
| Повтор после потери ответа | Сервер применяет пакет, ответ теряется, очередь остаётся. Повтор с тем же ID подтверждается без второй записи истории. |
| Два оператора, общая IndexedDB | Две вкладки доходят до подписания разных сканеров до начала фиксации. Только одна транзакция сохраняется: одна выдача, один пакет и одна запись истории. |
| Два независимых офлайн-терминала | Сервер принимает первую выдачу и отклоняет вторую. У проигравшего терминала сохраняются подпись, изменения и локальный журнал; конфликт явно показан. |
| Автоматическая замена | Отдельная проверка ранее включённого режима: один проверенный пакет с двумя изменениями, один активный сканер у получателя, блокировка снимается. |
| Возврат и отмена выдачи | Существующие браузерные регрессионные тесты прошли. |
| Реальные SQL-ограничения | Штатные тесты в отдельной PGlite-базе проверяют конфликт замены без частичной записи, атомарную замену, повтор одного ID, конфликт одного получателя и атрибуцию операторов. |

## Ограничения и оставшиеся риски

- Два независимых терминала без связи не могут заранее узнать о выдачах друг друга. До ответа сервера операции предварительные. Существующее серверное ограничение принимает одну выдачу; второй терминал сохраняет конфликт для сверки. Автоматически отбрасывать такую операцию или угадывать физическое местонахождение оборудования нельзя.
- Уже существовавшие конфликтные пакеты остаются в очереди. Исправление предотвращает новые локальные нарушения, но не переписывает старые операции и не согласует рабочие данные автоматически.
- Проверка относится к коду репозитория. Не проверялись фактически установленные миграции рабочей Supabase, опубликованный сайт, реальные сканеры и другие браузеры. Рабочие данные, RLS, RPC и миграции не менялись.
- Изменения не публиковались и не объединялись с `main`.
