# Внедрение v12

## Состояние до переключения

Проверено 13 ноября 2026 года: `devices` и `movements` имеют разрешающие политики `ALL ... true`; аккаунтов Supabase Auth нет. В базе уже существует заготовка `scanner_transactions`, но старый клиент не использует её RPC. Поэтому нельзя включать новые права до настройки администратора и готовности нового клиента.

## Порядок

1. Согласуйте короткое окно переключения. Остановите выдачу на старых вкладках. На каждом терминале дождитесь отправки очереди. Если это невозможно, сохраните локальные данные и очередь; не очищайте профиль браузера.
2. Создайте первый аккаунт приложения в Supabase Dashboard → Authentication → Users. Пароль задавайте в панели, не публикуйте и не добавляйте в репозиторий. Это отдельный аккаунт от входа владельца в Dashboard. Не включайте публичную регистрацию ради доступа к складу.
3. В SQL Editor установите `sklad.admin_email` и выполните `supabase/provision-admin.sql`. Убедитесь, что членство относится к нужному подтверждённому пользователю. В репозитории хранится только шаблон; фактический email в коммит не нужен.
4. Примените миграцию `20261113103823_harden_scanner_access.sql`. Она проверяет наличие первого администратора и отказывается менять доступ без него. Для существующего проекта используйте reviewed migration через Supabase CLI или MCP. Для нового локального проекта сначала создайте тестового администратора.
5. Проверьте: без входа чтение/изменение запрещены; администратор входит; оператор видит парк, но не может списывать и управлять копиями. Проверьте возвращение конфликта для устаревшей версии и повтор одного `p_id`.
6. Опубликуйте весь статический набор из одной ревизии. Закройте старые вкладки; откройте новую версию. Не очищайте IndexedDB для обновления. Для v12 доступны миграция хранилища и защита старой очереди от автоматической перезаписи.
7. Зайдите первым администратором. Проверьте количество устройств, выдачи, ремонт и последнюю синхронизацию. Выполните контрольную выдачу/возврат на выделенном тестовом устройстве, затем проверьте журнал.
8. Создайте первую серверную копию и проверьте её скачивание/сравнение. Убедитесь, что задание `sklad-daily-backup` существует в `cron.job`; проверьте `cron.job_run_details` на следующий день. При отсутствии pg_cron настройте поддерживаемый серверный планировщик до завершения внедрения.
9. Настройте отдельный внешний бэкап или PITR. Проверьте восстановление в изолированной базе, не заменяя рабочий парк.

Пример первого шага SQL (подставляется только в SQL Editor):

```sql
select set_config('sklad.admin_email', 'your-email@example.com', false);
-- Затем выполнить supabase/provision-admin.sql в том же SQL-сеансе.
```

Для предоставления роли используйте точный ID уже созданного пользователя:

```sql
insert into scanner_private.members(user_id,role)
values ('UUID_FROM_AUTH_USERS', 'operator')
on conflict(user_id) do update set role=excluded.role;
```

Удаление членства закрывает серверный доступ немедленно. Политики не используют редактируемое `user_metadata`.

## Неотправленная очередь старой версии

В новой версии она помечается для сверки. Скачайте её через диагностику; сравните физическое состояние, облачный парк и журнал. Администратор может принять облачное состояние: рассмотренные операции останутся в локальном архиве конфликтов. Утерянные по факту события оформляйте новыми подтверждёнными операциями после сверки. Не пересылайте старые безусловные upsert в закрытую базу.

## Проверки и откат

Перед миграцией выгрузите полный снимок таблиц, схемы и текущих политик в защищённое хранилище. Миграция не удаляет рабочие устройства/историю; списание логическое. При ошибке клиента откатывайте к предыдущей **совместимой защищённой** версии. Не возвращайте `allow_all` и анонимную запись ради запуска старого клиента. На время ремонта приостановите операции и сохраните локальные очереди.

## Отдельные риски вне клиента

- В проекте есть `warehouse_equipment`, `warehouse_workers`, `warehouse_logs` с выключенным RLS и разрешающими политиками. Текущий репозиторий их не использует; назначение неизвестно. Не включайте RLS вслепую: выясните потребителей и согласуйте отдельные политики. [Документация RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).
- Удаление встроенного слепка из новых файлов не удаляет его из старых коммитов и чужих копий. С владельцем репозитория отдельно согласуйте переписывание истории и, при необходимости, запрос GitHub на очистку кэшей. Не выполняйте force-push без проверки веток, тегов и потребителей.
- Наличие роли в локальном офлайн-кэше не является серверной авторизацией. Все RPC проверяют текущую запись членства; терминал должен регулярно выходить в сеть.
