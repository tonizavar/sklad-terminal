# ID оператора, личный PIN и журнал создателя

Оператор программы и получатель сканера — разные сотрудники. Перед работой оператор вводит свой ID и PIN. Поле бейджа в форме выдачи по-прежнему относится к получателю оборудования.

## Начало работы

Создатель получает одноразовый ключ первоначальной настройки вне публичного репозитория. В форме настройки он указывает свой ID, задаёт PIN из 6–12 цифр и повторяет его. После использования ключ аннулируется. В журнале появляется событие настройки создателя.

Сотрудник выбирает «Первый вход», указывает свой ID и самостоятельно задаёт PIN из 6–12 цифр с повтором. После регистрации сразу открывается рабочий терминал; одноразовый ключ сотруднику не нужен.

В разделе «Операторы и PIN» создатель видит зарегистрировавшихся сотрудников. При необходимости он также может добавить ID сотрудника, необязательное имя и начальный PIN. PIN не отображаются в списке и не доступны через API чтения. Там же можно заменить PIN или отключить доступ. Новый PIN передаётся сотруднику отдельно, не через общий журнал.

## Что видит создатель

Раздел «Журнал сотрудников» содержит ID автора, имя, время получения события сервером, терминал, тип действия и результат. Для изменений устройства доступны фактические состояния до и после операции. Есть фильтр по ID и периоду до 31 суток, постраничная загрузка и CSV с деталями изменений.

Записываются выдача, возврат, ремонт, регистрация/списание, изменения устройств, конфликты, входы/выходы, добавление/отключение сотрудников, смена PIN, операции с копиями, экспорт отчётов и запрос печати акта. Печать фиксируется как запрос из программы, а не доказательство физической печати. Произвольные запросы к базе вне интерфейса и каждое движение мыши не являются действиями интерфейса.

Старые записи не получают вымышленного автора: для них выводится «автор не указан». ID получателя сканера не используется для определения автора операции.

## Офлайн и смена оператора

Действия с устройствами подписываются ключом проверенной сессии **до** локальной транзакции. В одной транзакции записываются устройство, автор и пакет очереди. Подписанный пакет можно доставить позже, в том числе после выхода или входа другого сотрудника: автором остаётся исходный оператор. Подмена ID, содержимого пакета или подписи отклоняется сервером.

Подпись сохраняет целостность и привязку к сессии, но не является юридической электронной подписью. Время создания офлайн-события задаётся устройством; отдельно фиксируется достоверное время получения сервером. Ранее сохранённые пакеты принимаются после выхода, если они созданы в допустимом окне сессии. Сессия действует 12 часов; после её истечения для новых операций нужен онлайн-вход.

Выйти и сменить сотрудника можно через верхнюю панель. Офлайн-выход тоже сохраняется в очереди. Старые неподписанные пакеты прежних версий не приписываются текущему оператору: их нужно отдельно скачать и сверить создателю.

## Защита

PIN проверяется на сервере, хранится только bcrypt-хеш. После пяти неудачных попыток для ID вход ограничивается на 15 минут; также есть ограничение по источнику запросов. Токен сессии случайный, хранится только его хеш на сервере; клиент хранит активную сессию в sessionStorage этой вкладки. PIN и токены не добавляются в журнал и логические JSON-копии.

Сотрудник не может открыть журнал создателя, управлять PIN, списывать/регистрировать оборудование или работать с резервными копиями. Эти проверки выполняет сервер. На приватные таблицы операторов, сессий и аудита нет прямого доступа. Журнал нельзя очистить через интерфейс или публичный API.

Профиль браузера содержит локальный кэш склада и очередь; PIN не шифрует эти файлы на диске. Для общего поста нужна блокировка рабочего места и контроль доступа к профилю ОС. Личные PIN нельзя передавать другому сотруднику.

## Внедрение

1. Сохранить копию парка и истории.
2. Применить миграцию `operator_pin_audit`. До переключения флага `operator_config.enabled` сохраняется совместимость с прежним общим клиентом.
3. Подготовить случайный одноразовый ключ, сохранить его хеш и согласованный ID создателя в приватной конфигурации. Ключ выдать владельцу отдельным приватным файлом, не коммитить.
4. Опубликовать клиент целиком и включить обязательный PIN (`enabled=true`). Неподтверждённые чтения и старые неподписанные изменения после этого закрыты.
5. Создатель завершает настройку PIN, после чего сотрудники регистрируются самостоятельно. Старые вкладки нужно обновить без очистки IndexedDB.
6. Проверить вход, выдачу/возврат, журнал, офлайн-пакет после смены оператора и серверное расписание копий.

Суточные логические копии включают парк, движения, аудит и непарольные сведения об операторах. Полное аварийное восстановление учётных данных требует защищённого бэкапа базы; JSON-снимки специально не содержат хешей PIN и ключей сессий.

## Самостоятельная регистрация · v15

`scanner_operator_register` доступен без сессии, но создаёт только обычного оператора. Регистрация разрешена после настройки создателя. Его ID зарезервирован. Повторный запрос не заменяет существующий PIN и не включает отключённый аккаунт. Событие самостоятельной регистрации фиксируется в журнале.

Кто знает адрес сайта, может зарегистрировать свободный ID и получить обычный доступ к складу. Подтверждение PIN означает владение учётной записью, но не проверяет личность или принадлежность ID через кадровую систему. Это выбранный режим самостоятельного первого входа; создатель может отключать лишние аккаунты.

Ограничение регистрации: 10 попыток на источник за 15 минут и 100 попыток суммарно за час. Ограничение входа по PIN действует отдельно. PIN не попадает в аудит или JSON-копии.

Для обновления с v14 достаточно применить миграцию `self_registration` и опубликовать статические файлы. Повторная настройка создателя и замена PIN действующих сотрудников не нужны.
