# Порядок разработки

## Начало задачи

1. Открой корень SCANNER-CONTROL как основной каталог локального проекта Codex и создай в нём новый чат.
2. Проверь ветку, HEAD, `git status --short --branch`, `git diff` и `git diff --cached`. Сохрани незавершённые правки. Для отдельной задачи выбирай локальную ветку от проверенной базы без переноса чужих изменений.
3. Найди сценарий в коде и существующих тестах. Воспроизведи сбой на синтетических данных. Проверь самый короткий путь сканером и клавиатурой для изменений выдачи и приёмки.

## Проверки в PowerShell

Требуются Git и Node.js 22+ с npm. Команды выполняй из корня репозитория. В Windows можно вызвать `npm.cmd` и `npx.cmd`.

```powershell
npm.cmd ci --ignore-scripts
npm.cmd run check
npm.cmd test
npx.cmd playwright install chromium
npm.cmd run test:browser
git diff --check
git status --short --branch
```

На этом ПК зависимости из lock-файла уже подготовлены. Если в PATH текущей оболочки нет Git, используй `& 'C:/Program Files/Git/cmd/git.exe' status --short --branch`. Если Node.js или npm отсутствуют в PATH, Codex может использовать Node.js из пакета Codex Primary Runtime. Ниже приведены эквивалентные команды для уже подготовленной папки.

```powershell
$runtime = Get-AppxPackage -Name 'OpenAI.CodexPrimaryRuntime*' |
  Sort-Object Version -Descending | Select-Object -First 1
$nodeDir = Join-Path $runtime.InstallLocation 'dependencies/node/bin'
$env:Path = "$nodeDir;$env:Path"
$check = (Get-Content -Raw package.json | ConvertFrom-Json).scripts.check
cmd.exe /d /c $check
node --run test
$env:PLAYWRIGHT_CHROMIUM_EXECUTABLE = 'C:/Program Files/Google/Chrome/Application/chrome.exe'
node node_modules/@playwright/test/cli.js test
```

Установка Chromium нужна один раз для закреплённой версии Playwright. При наличии установленного Chrome или Edge можно задать `PLAYWRIGHT_CHROMIUM_EXECUTABLE` путём к браузеру и пропустить установку Chromium. Сценарии Playwright запускают свой сервер на порту 4173; если он занят, выбери свободный порт через `PLAYWRIGHT_PORT`. Для изменений документации достаточно проверить пути, команды и diff. В Windows тесты настраиваются по `package-lock.json` и `.github/workflows/check.yml`.

## Изоляция рабочей базы

`node tests/server.cjs` только раздаёт файлы. Открытая в обычном браузере страница по умолчанию использует рабочий адрес Supabase из `app.js`. Для ручной проверки без сети к рабочей базе сначала заблокируй её домен в отдельном тестовом браузере либо используй отдельную тестовую конфигурацию с тестовым Supabase и соответствующим `connect-src`. Для полной имитации операций используй штатные сценарии Playwright. Для SQL используй PGlite. Рабочие ID, токены, журнал, снимки и очереди в тесты не переносить.

## Перед публикацией

- Проверь diff и результаты тестов. Опиши, как проверить затронутый сценарий и откатить изменения. Для SQL укажи миграции, изменения полномочий и влияние на существующие данные и очереди.
- При изменении статики проверь версию кэша и повторный запуск без сети. Для выдачи, возврата и замены проверь повторный скан, конфликт версий и сохранность очереди.
- После первой публикации механизма автообновления уже открытые старые вкладки нужно один раз открыть заново. Для отката публикуй прежние ресурсы под новой версией `CACHE`, чтобы открытые вкладки получили их как очередное обновление.
- Оставь изменения локально и передай владельцу результаты проверки. Push, merge, обновление GitHub Pages и любые операции с рабочей базой требуют явного разрешения владельца.

### Переход на PIN

1. Перед публикацией проверь, что создатель располагает ранее установленным PIN. Самостоятельный первый вход для учётной записи создателя закрыт. Выбери паузу между операциями и проверь состояние очереди на рабочих постах.
2. По согласованию примени `20261114190759_restore_pin_and_track_terminals.sql` и сразу опубликуй клиент из `main`. После миграции старый экран входа по ID уже не выдаёт сессии. Попроси сотрудников с открытыми вкладками дождаться обновления или переоткрыть их и войти по PIN. Для ID, созданных без PIN, нажать «Первый вход / создать PIN».
3. Проверь вход создателя, первый вход сотрудника, отправку сохранённой очереди и отображение постов. Откат интерфейса готовь как отдельный коммит с новой версией кэша и сохранением формы PIN. Версия с входом по одному ID несовместима с миграцией. При сбое базы не восстанавливай рабочие данные и не включай старый вход автоматически.
